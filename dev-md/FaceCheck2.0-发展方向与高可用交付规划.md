# FaceCheck 2.0 发展方向与高可用交付规划

> 项目：FaceCheck：一起刷脸签到  
> 当前基线：README.md 标注的 FaceCheck v1.3  
> 规划目标：在 v1.3 已完成的刷脸签到闭环基础上，升级为更完整、更可信、更适合期末展示的 HarmonyOS 原生课堂考勤系统  
> 技术栈：ArkTS + ArkUI + ArkData RelationalStore + Preferences + Camera Kit / Image Kit + Core Vision Kit + Vision Kit Interactive Liveness + Location Kit  
> 规划日期：2026-07-05  

## 1. 重新校准：当前不是 v1.1，而是 v1.3

根据 `README.md`，当前 FaceCheck 已经进入 v1.3。后续规划必须以 v1.3 为基线，而不是继续围绕早期版本补基础功能。

v1.3 已完成的关键能力如下：

| 模块 | v1.3 当前状态 | 2.0 中的定位 |
| --- | --- | --- |
| 人员管理 | 学生信息增删改查，支持班级归属，人脸录入状态刷新 | 保持主流程稳定，补充更清晰的异常提示和批量演示数据 |
| 教学组织 | 班级、课程、选课关系管理 | 作为地理围栏和报表统计的基础实体 |
| 人脸录入 | 前置相机拍照，单人正面检测，质量评估，保存注册照片 | 继续稳定化，不把 1:N 作为主线 |
| 刷脸签到 | 按课程发起签到，冻结本场应到名单，选择学生后做 1:1 人脸比对 | 作为 2.0 主流程核心，新增位置校验前置环节 |
| 活体检测 | 可选交互式活体检测，已接入真实设备流程 | 继续保留开关，并加强失败原因、设备能力提示 |
| 缺勤记录 | 结束场次时自动为未签到成员生成缺勤记录 | 已完成基础闭环，2.0 只做展示、导出、报表深化 |
| 考勤统计 | 应到、已到、迟到、缺勤、出勤率圆环 | 保证不出现 NaN、undefined、圆环不刷新等展示问题 |
| 实时动态 | 横屏、竖屏均已有动态状态展示思路 | 2.0 增加位置失败、活体失败、人脸失败的结构化原因 |
| 考勤记录 | 支持场次、班级、日期筛选、搜索与 CSV 导出 | 增加位置字段、失败尝试日志、汇总报表 |
| 设置 | 人脸阈值、迟到判定、活体开关、数据清除 | 增加位置策略、设备能力检测、诊断导出 |
| PlanUI | 5 个可复用组件，响应式布局，动效系统已完成 | 不推倒重做，只基于 PlanUI 追加地理围栏和报表视图 |

因此，FaceCheck 2.0 的重点不再是“把基础刷脸签到做出来”，而是：

- 加上课堂现场约束：地理围栏。
- 加上失败可解释性：结构化失败原因与尝试日志。
- 加上最终产品感：报表、权限体验、诊断、演示脚本。
- 加上高可用保障：真机回归、横竖屏、生命周期、数据库迁移、隐私边界。

## 2. 2.0 产品定位

FaceCheck 2.0 建议定位为：

```text
面向课堂场景的端侧可信考勤系统：
课程名单快照 + 地理围栏 + 活体检测 + 1:1 人脸比对 + 缺勤生成 + 记录报表
```

完整签到判定链路应为：

```text
存在进行中的签到场次
+ 学生属于本场应到名单
+ 学生未重复签到
+ 地理围栏校验通过或本场未启用地理围栏
+ 活体检测通过或系统设置未启用活体检测
+ 现场照片检测到合格单人正脸
+ 现场照片与注册照片 1:1 比对通过
= 签到成功
```

这条链路的价值是：

- “是谁”：由人脸比对确认。
- “是否真人在场”：由活体检测确认。
- “是否在教室附近”：由地理围栏确认。
- “是否属于本堂课”：由课程、班级、选课关系和场次快照确认。
- “为什么失败”：由失败原因和尝试日志解释。
- “结果能否复核”：由记录页、CSV、报表和诊断日志支持。

当前 FaceCheck 是“老师拿一台华为 Pad 给学生轮流刷脸”的课堂设备模式，所以 2.0 的地理围栏不解释为“验证每个学生自己的手机位置”，而是解释为：

```text
老师发起签到时，获取当前 Pad 位置作为本场签到地点；
每次学生站到 Pad 前刷脸签到时，再获取当前 Pad 位置；
若当前 Pad 仍在本场签到地点允许半径内，则继续活体检测和人脸比对。
```

这样能证明“本场签到设备位于课堂现场”，再结合活体检测和人脸比对证明“当前刷脸的人是本人”。如果未来扩展学生端 App，才需要把位置校验下放到每个学生自己的设备。

## 3. 本周优先任务：跑通三个相关案例

老师要求本周在设备上跑通三个与期末作业相关的案例，并截图提交。建议直接围绕 FaceCheck 的三条核心能力做案例验证。

### 3.1 案例一：Core Vision Kit 人脸检测与 1:1 比对

目标：

- 验证华为 Pad 上 Core Vision Kit 的人脸检测能力可用。
- 验证注册照片和现场照片可以完成 1:1 比对。
- 验证无人脸、多人脸、侧脸、质量差照片能被拦截。

对应项目模块：

- `entry/src/main/ets/kits/FaceVisionAdapter.ets`
- `entry/src/main/ets/pages/FaceEnrollPage.ets`
- `entry/src/main/ets/pages/Index.ets`
- `entry/src/main/ets/services/AttendanceService.ets`

截图建议：

- 人脸录入成功页面。
- 签到成功结果卡片，显示匹配分数。
- 人脸检测失败场景，如未检测到人脸或多人脸。

验收标准：

- 合格正脸能录入。
- 本人 1:1 比对通过。
- 非本人或低质量图像被拒绝。
- 日志中没有资源泄露、未捕获异常或页面卡死。

### 3.2 案例二：Vision Kit 交互式活体检测

目标：

- 验证交互式活体检测能启动、完成并返回可用于后续比对的图像。
- 验证横屏进入活体时能临时切到竖屏，返回后恢复布局。
- 验证活体成功后继续进入人脸比对与签到写入。

对应项目模块：

- `entry/src/main/ets/kits/LivenessAdapter.ets`
- `entry/src/main/ets/pages/Index.ets`
- `entry/src/main/ets/services/SettingsService.ets`

截图建议：

- 活体检测系统页。
- 活体成功返回 FaceCheck。
- 开启活体后的完整签到成功页。

验收标准：

- 活体成功时标记 `livenessPassed=true`。
- 活体取消或失败不写入正式签到成功记录。
- 返回后页面不卡死、不白屏、不丢失当前场次。

### 3.3 案例三：Location Kit 当前定位与地理围栏判断

目标：

- 验证设备可以申请位置权限并获取当前位置。
- 验证可以基于教师设置的中心点和半径判断“围栏内/围栏外”。
- 为 FaceCheck 2.0 的位置防作弊功能打底。

建议技术路线：

- 使用 `@kit.LocationKit` 获取当前定位。
- 运行时申请 `ohos.permission.APPROXIMATELY_LOCATION`，必要时再使用 `ohos.permission.LOCATION`。
- 使用 Haversine 公式在本地计算当前位置到签到中心点的距离。
- 2.0 第一版采用“前台签到时即时定位判断”，暂不做后台持续地理围栏，避免权限与后台保活复杂度过高。

计划新增模块：

- `entry/src/main/ets/models/LocationModel.ets`
- `entry/src/main/ets/kits/LocationAdapter.ets`
- `entry/src/main/ets/services/GeoFenceService.ets`
- `entry/src/main/ets/components/LocationStatusCard.ets`

截图建议：

- 位置权限申请。
- 定位成功结果，显示经纬度、精度和时间。
- 围栏内通过。
- 围栏外失败。

验收标准：

- 权限拒绝时有清晰提示，不崩溃。
- 定位超时时可重试。
- 距离计算稳定，边界值可解释。
- 位置校验结果可以进入签到流程和记录页。

## 4. 2.0 功能优先级

### P0：地理围栏最小闭环

这是最推荐的加分功能。原因是它与课堂考勤高度相关，技术上能体现 HarmonyOS 原生 Location Kit，答辩时也容易讲清楚。

最小闭环包括：

- 发起签到时选择是否启用位置校验。
- 以教师当前定位作为签到点。
- 设置地点名称和允许半径。
- 每次刷脸签到前获取当前 Pad / 签到设备位置。
- 判断当前位置是否在半径内。
- 围栏内继续活体与人脸比对。
- 围栏外不写入成功记录，并显示失败原因。
- 记录页和导出文件中能看到位置校验结果。

### P1：失败尝试日志

v1.3 已经能展示正式考勤记录，但对于失败场景，最好增加单独的“尝试日志”。

它解决的问题是：

- 学生说“我签了但失败了”，老师能看到失败原因。
- 活体失败、位置失败、人脸失败不会污染正式出勤率。
- 期末演示时可以展示系统的可解释性。

建议记录的失败阶段：

```text
NO_ACTIVE_SESSION
NOT_SESSION_MEMBER
DUPLICATE_CHECK_IN
FACE_NOT_ENROLLED
LOCATION_PERMISSION_DENIED
LOCATION_TIMEOUT
OUT_OF_GEOFENCE
LIVENESS_CANCELLED
LIVENESS_FAILED
NO_FACE_DETECTED
MULTIPLE_FACE_DETECTED
FACE_NOT_FRONTAL
FACE_COMPARE_FAILED
FACE_SCORE_TOO_LOW
DATABASE_WRITE_FAILED
```

### P2：报表与导出增强

v1.3 已经支持记录筛选和 CSV 导出，2.0 应在这个基础上增强，而不是重做。

建议增加：

- 按课程统计：总场次、平均出勤率、迟到次数、缺勤次数。
- 按班级统计：班级出勤率排行。
- 按学生统计：个人出勤率、迟到次数、缺勤次数。
- 按场次统计：应到、实到、迟到、缺勤、失败尝试数。
- CSV 增加位置校验列、失败原因列。

### P3：演示数据与交付材料

为了保证答辩稳定，建议增加演示数据初始化能力。

设置页可以增加：

- 生成演示班级。
- 生成演示课程。
- 生成演示学生。
- 生成演示场次与历史考勤记录。
- 清除演示数据。

注意：

- 演示数据不应覆盖真实人脸照片。
- 演示学生要有明确标识。
- 可以只生成组织关系和记录，不生成可用于真实人脸比对的照片。

### P4：1:N 自动识别探索

当前 README 明确说明项目是“选择学生后的 1:1 人脸验证”，这条主线是正确的。

1:N 自动识别可以作为探索项，但不建议作为期末交付硬目标：

- 性能和误识别风险更高。
- 如果 Core Vision Kit 不提供稳定的人脸特征向量检索，不应强行手写识别算法。
- 可以做成“候选人推荐 + 老师确认”：系统按本场应到名单逐个比对，取最高分候选人，但最终仍需确认。

结论：

- 期末主流程继续保持 1:1，保证可靠。
- 1:N 只作为加分演示，不影响主流程验收。

## 5. 地理围栏详细设计

### 5.1 场景规则

教师发起签到时可配置：

- 是否启用位置校验。
- 是否使用当前位置作为签到点。
- 签到点名称，如“教学楼 A306”。
- 允许半径，如 50m、100m、200m、300m。

每次学生站到 Pad 前刷脸签到时，系统检查当前 Pad / 签到设备位置：

- 当前场次是否启用位置校验。
- 应用是否已有位置权限。
- 当前定位是否成功。
- 当前定位精度是否可接受。
- 当前距离是否在允许半径内。

结果：

- 未启用位置校验：沿用 v1.3 原流程。
- 围栏内：继续活体检测与人脸比对。
- 围栏外：显示“当前位置距离签到点 X 米，超出允许范围 Y 米”，并写入失败尝试日志。
- 定位失败：允许重试，不写入成功记录。

### 5.2 权限策略

推荐策略：

- 默认不在启动时申请位置权限。
- 只有教师开启位置校验，或本场已启用位置校验且即将刷脸签到时，才申请位置权限。
- 优先申请近似位置权限，若距离判断需要更高精度，再提示精确位置授权。
- 不做后台定位，不做连续轨迹记录。

这样可以降低隐私压力，也更符合课堂签到场景。

### 5.3 数据库 v4 设计

v1.3 README 提到数据库已经到 v3。FaceCheck 2.0 如加入地理围栏，建议升级到 v4。

`attendance_sessions` 新增字段：

```text
enable_location_check INTEGER NOT NULL DEFAULT 0
location_name TEXT
latitude REAL
longitude REAL
radius_meters INTEGER NOT NULL DEFAULT 100
location_accuracy REAL
```

含义：

- 保存教师发起场次时的围栏配置。
- 如果未启用位置校验，字段可为空或保持默认值。

`attendance_records` 新增字段：

```text
check_latitude REAL
check_longitude REAL
check_location_accuracy REAL
distance_meters REAL
location_passed INTEGER NOT NULL DEFAULT 1
location_fail_reason TEXT
```

含义：

- 保存正式成功或迟到记录中的位置结果。
- 对缺勤记录，位置字段通常为空。

新增 `check_in_attempts` 表：

```text
id INTEGER PRIMARY KEY AUTOINCREMENT
session_id INTEGER NOT NULL
user_id INTEGER
attempt_time INTEGER NOT NULL
stage TEXT NOT NULL
success INTEGER NOT NULL
fail_reason TEXT
compare_score REAL
liveness_passed INTEGER
location_passed INTEGER
distance_meters REAL
created_at INTEGER NOT NULL
```

含义：

- 保存失败尝试和关键成功尝试。
- 不参与正式出勤率计算。
- 用于实时动态、记录详情、诊断导出和答辩演示。

推荐索引：

```text
idx_records_session_user
idx_records_status_time
idx_sessions_course_time
idx_attempts_session_time
idx_attempts_user_time
```

### 5.5 签到流程调整

推荐顺序：

```text
检查当前场次
-> 检查应到名单
-> 检查重复签到
-> 地理围栏校验
-> 活体检测
-> 相机拍照
-> 人脸质量检测
-> 人脸 1:1 比对
-> 判定正常或迟到
-> 写入正式记录
-> 写入尝试日志
-> 刷新统计、圆环和实时动态
```

原因：

- 重复签到放在位置前，减少无意义权限弹窗。
- 地理围栏放在人脸前，减少不在场学生占用活体和 AI 比对资源。
- 尝试日志放在最后统一写入，保证每个失败阶段都有可追踪结果。

## 6. UI 与可用性优化

v1.3 已完成 PlanUI 设计系统，因此 2.0 不建议重新设计整套 UI。正确方向是“在现有 PlanUI 上补齐新状态和新流程”。

### 6.1 首页工作台

首页新增信息应围绕“当前场次是否可信”展开：

- 当前课程、班级、场次状态。
- 地理围栏状态：未启用、定位中、范围内、范围外、权限拒绝。
- 活体状态：未启用、待检测、通过、失败。
- 人脸状态：待拍照、质量合格、比对通过、比对失败。
- 出勤圆环继续显示绿色动态比例，默认无场次时显示 0%，不能出现 NaN 或 undefined。

横屏：

- 保持工作台三栏或主区域加右侧实时动态。
- 右侧实时动态列表支持滚动，失败尝试也应显示。

竖屏：

- 保持底部导航。
- 将实时动态放在可用空白区域或折叠区中。
- 内容高度不足时不强行撑爆页面。

### 6.2 发起签到面板

从“只选择课程”升级为“场次配置面板”：

- 课程选择。
- 场次标题自动生成，可编辑。
- 迟到时间设置。
- 活体检测提示。
- 位置校验开关。
- 使用当前位置作为签到点。
- 地点名称输入。
- 半径选择。
- 定位结果预览。

交互原则：

- 默认仍能快速发起普通签到。
- 开启位置校验后必须看到定位结果。
- 定位失败不应导致应用崩溃，应允许重试或关闭位置校验。

### 6.3 记录页

v1.3 已支持场次、班级、日期筛选、搜索和 CSV 导出。2.0 增强为：

- 状态筛选增加“失败尝试”入口。
- 筛选项增加位置结果：全部、未启用、通过、失败。

### 6.4 设置页

建议分区：

- 识别策略：人脸阈值、活体开关、迟到判定。
- 位置策略：默认半径、定位超时、位置校验默认开关。

注意：README 已标注 Version 1.3，应用内版本展示后续也应同步到 1.3 或 2.0，避免答辩时出现文档和应用不一致。

### 6.5 空状态与错误提示

需要覆盖：

- 没有课程：引导去教学页创建课程。
- 课程没有学生：引导去人员页或教学页完成选课关系。
- 学生未录入人脸：引导去录入页面。
- 活体不支持：提示关闭活体后继续普通签到。
- 位置权限拒绝：提示授权或关闭位置校验。
- 定位超时：允许重试。
- 无当前场次：出勤率显示 0%，圆环为灰底 0 进度。

## 7. 高可用工程优化

### 7.1 权限与设备能力检测

设置页建议展示设备能力：

- Camera 可用。
- Core Vision 人脸检测可用。
- Core Vision 人脸比对可用。
- Vision Kit 活体可用。
- Location Kit 定位可用。

权限申请策略：

- 相机权限：录入和签到拍照时申请。
- 位置权限：启用位置校验时申请。
- 不在后台定位，不申请多余权限。

### 7.2 生命周期稳定性

重点覆盖：

- 从系统相机返回。
- 从活体检测页面返回。
- 横竖屏切换。
- 应用进入后台再回到前台。
- 设备锁屏后重新进入。
- 覆盖安装后数据库迁移。

要求：

- 不重复写入签到记录。
- 不丢失当前场次。
- 不出现 NaN、undefined、空白圆环。
- 所有 PixelMap 和 Kit 资源都能重复释放。

### 7.3 数据库迁移策略

数据库 v4 必须保证：

- v1、v2、v3 数据可平滑迁移。
- 新字段都有默认值。
- 迁移失败有日志。
- 迁移完成后自动检查核心表与索引。
- 覆盖安装后旧记录仍能显示。

### 7.4 日志与诊断

建议日志分类：

- `AI_FACE`：人脸检测、质量评估、比对分数。
- `LIVENESS`：活体启动、取消、成功、失败、方向恢复。
- `LOCATION`：权限、定位、距离计算、围栏结果。
- `ATTENDANCE`：场次、名单、重复签到、记录写入。
- `DB`：迁移、查询、写入异常。
- `UI`：页面刷新、横竖屏、统计计算。

设置页可增加“导出诊断日志”，用于答辩前定位真机问题。

### 7.5 性能与资源

重点：

- PixelMap 使用后释放。
- Face detector / matcher 按需初始化，退出释放。
- 长列表使用 List，避免一次性渲染过多组件。
- 记录页统计尽量在数据加载后计算，不在每次 build 中重复大量计算。
- CSV 导出时禁用重复点击，并显示进度或结果提示。

## 8. 隐私与安全边界

FaceCheck 2.0 会同时处理人脸和位置两类敏感信息，必须在文档和答辩中说清楚边界。

建议策略：

- 人脸照片默认保存在设备应用沙箱。
- 位置只在签到瞬间采集，不做后台持续定位。
- 不保存连续轨迹。
- 只保存签到点、签到时位置、距离和通过结果。
- 设置页提供清除全部人脸与考勤数据。
- CSV 导出前提示可能包含个人信息。
- 测试结束后清理真实人脸数据。

答辩时可以强调：

```text
本项目是教学实践系统，不作为高安全级身份认证系统。
所有敏感数据默认本地保存，未设计服务器上传。
```

## 12. 风险与取舍

### 12.1 地理围栏风险

风险：

- 室内定位精度可能较差。
- Pad 可能没有 GPS，定位依赖 Wi-Fi 或网络。
- 权限流程在不同系统版本上表现不同。

应对：

- 默认半径不低于 100m。
- 展示定位精度，精度差时提示老师。
- 允许老师关闭位置校验。
- 答辩前准备固定测试点和截图。

### 12.2 活体检测风险

风险：

- 不同设备支持情况不同。
- 活体页面依赖系统组件，调试日志较复杂。

应对：

- 活体保持可开关。
- 普通人脸签到必须始终可用。
- 记录真机型号、系统版本和测试结果。

### 12.3 1:N 自动识别风险

风险：

- 性能不可控。
- 误识别风险更高。
- 可能需要稳定的人脸特征向量检索能力。

应对：

- 不作为 2.0 必做项。
- 只做“候选人推荐 + 老师确认”探索。
- 主流程继续保持 1:1，保证交付稳定。

## 13. 结论

FaceCheck v1.3 已经具备课堂刷脸签到的完整基础闭环，包括组织管理、人脸录入、1:1 签到、活体检测、缺勤记录、统计圆环、实时动态、记录筛选和 CSV 导出。

FaceCheck 2.0 最值得投入的方向是：

```text
地理围栏 + 失败尝试日志 + 位置字段导出 + 多维报表 + 真机案例验证 + 高可用交付材料
```

这条路线既符合老师提到的“地理围栏等功能拓展有加分”的方向，也能体现 HarmonyOS 原生能力整合：

- Core Vision Kit 负责人脸检测与比对。
- Vision Kit 负责交互式活体检测。
- Location Kit 负责课堂现场性校验。
- ArkData 负责本地持久化、场次快照和历史记录。
- ArkUI 与 PlanUI 负责横竖屏下的高质量使用体验。

最终目标不是“能跑一次”，而是老师拿到 Pad 后能完成一套真实课堂流程：建班、建课、录脸、发起签到、现场核验、生成缺勤、查看报表、导出数据、说明隐私与测试结果。
